DevOps Automation

Simple Bash scripts that save hours every week.

How small, repeatable automation scripts can help manage database backups, log cleanup, disk threshold warnings, and routine Linux server administration on AWS EC2.

By Muhammad Zain Linux Administration & Automation 5 min read Bash · AWS CLI · Cron · Linux

The DevOps Swiss Army Knife

While modern tools like Ansible, Terraform, and Kubernetes get the headlines, a solid understanding of shell scripting remains one of the highest-leverage skills in cloud and DevOps engineering. When you manage Linux virtual machines on AWS EC2 or Amazon Linux, you inevitably face repetitive operational tasks: rotating bloated log files, backing up database dumps, and syncing files to remote storage.

Writing compact, robust Bash scripts and delegating them to cron jobs frees up valuable engineering hours and eliminates human error.

Rule of thumb: If you find yourself typing the exact same sequence of terminal commands more than twice a week, wrap it in a tested Bash script.

Script 1: Automated MySQL Backup with S3 Sync

Database backups are only useful if they run consistently and are copied off the host machine immediately. This script generates a compressed database dump with a precise timestamp, uploads it directly to an Amazon S3 bucket using the AWS CLI, and deletes local dumps older than 7 days.

backup-mysql-s3.sh 
#!/usr/bin/env bash
set -euo pipefail

# Configurations
TIMESTAMP=$(date +"%Y%m%d_%H%M%S")
BACKUP_DIR="/var/backups/mysql"
DB_NAME="app_production"
S3_BUCKET="s3://my-company-db-backups-secure/mysql"
BACKUP_FILE="${BACKUP_DIR}/${DB_NAME}_${TIMESTAMP}.sql.gz"

mkdir -p "${BACKUP_DIR}"

echo "==> Starting backup for ${DB_NAME} at $(date)..."

# Dump database and compress on the fly
mysqldump --single-transaction --quick --routines "${DB_NAME}" | gzip > "${BACKUP_FILE}"

echo "==> Database dump completed: ${BACKUP_FILE}"

# Sync file to AWS S3 bucket
aws s3 cp "${BACKUP_FILE}" "${S3_BUCKET}/${DB_NAME}_${TIMESTAMP}.sql.gz" --sse AES256

echo "==> Uploaded successfully to S3."

# Cleanup local backups older than 7 days to preserve disk space
find "${BACKUP_DIR}" -type f -name "*.sql.gz" -mtime +7 -delete
echo "==> Local retention cleaned up."

Script 2: Log Archival & Disk Out-of-Space Prevention

One of the most frequent causes of unannounced server downtime is an application filling up the root partition (/var/log or /) with debug logs. The following script scans application log directories, compresses logs older than 3 days, and purges archives older than 14 days.

cleanup-logs.sh 
#!/usr/bin/env bash
set -euo pipefail

LOG_DIR="/var/log/application"
ARCHIVE_DIR="/var/log/application/archive"

mkdir -p "${ARCHIVE_DIR}"

echo "==> Compressing uncompressed logs older than 3 days..."
find "${LOG_DIR}" -maxdepth 1 -type f -name "*.log" -mtime +3 -exec gzip {} \;

echo "==> Moving compressed archives..."
find "${LOG_DIR}" -maxdepth 1 -type f -name "*.gz" -exec mv {} "${ARCHIVE_DIR}" \;

echo "==> Removing archives older than 14 days..."
find "${ARCHIVE_DIR}" -type f -name "*.gz" -mtime +14 -delete

echo "==> Disk maintenance complete. Current disk usage:"
df -h "${LOG_DIR}"

Script 3: Proactive Disk & Memory Health Watchdog

Before an incident escalates to users, a lightweight Bash watchdog can evaluate disk utilization and free RAM percentage, logging an alert or triggering an automated notification if usage exceeds safe thresholds (e.g., 85%).

system-watchdog.sh 
#!/usr/bin/env bash

DISK_THRESHOLD=85
CURRENT_DISK=$(df -h / | awk 'NR==2 {print $5}' | tr -d '%')

if [ "${CURRENT_DISK}" -ge "${DISK_THRESHOLD}" ]; then
    echo "[CRITICAL] Root partition disk usage is at ${CURRENT_DISK}%!"
    # You can trigger a curl webhook to Slack or send an AWS SNS email here
else
    echo "[HEALTHY] Disk usage is at ${CURRENT_DISK}%."
fi

Best Practices for Production Scripts

Writing scripts that run unsupervised at 3:00 AM requires defensive programming. Here are the core habits I incorporate into every production script:

  • set -euo pipefail: Exit immediately if any command returns a non-zero code (-e), treat uninitialized variables as errors (-u), and catch failures inside pipes (-o pipefail).
  • Always quote variables: Wrap variables in double quotes ("${MY_VAR}") to prevent unexpected word splitting and wildcard expansions.
  • Explicit absolute paths: When running from cron, never rely on standard $PATH. Specify explicit binary paths (e.g. /usr/bin/aws) or declare PATH=/usr/local/bin:/usr/bin:/bin at the top.
  • Structured logging: Pipe script output with timestamps to dedicated log files so failed executions leave an audit trail.

Automating with Crontab

To run these scripts automatically on an Amazon Linux EC2 instance, install them into /usr/local/bin/ and register entries in the crontab:

crontab -e 
# Daily MySQL backup to AWS S3 at 02:00 AM
0 2 * * * /usr/local/bin/backup-mysql-s3.sh >> /var/log/backup-mysql.log 2>&1

# Daily log cleanup at 03:30 AM
30 3 * * * /usr/local/bin/cleanup-logs.sh >> /var/log/cleanup-logs.log 2>&1

# Hourly system health watchdog check
0 * * * * /usr/local/bin/system-watchdog.sh >> /var/log/system-watchdog.log 2>&1

Summary

Automating repetitive maintenance tasks with clean, error-tolerant Bash scripts dramatically improves server stability and frees you to work on higher-impact cloud architecture tasks. Start small, write defensively, and test every edge case.
