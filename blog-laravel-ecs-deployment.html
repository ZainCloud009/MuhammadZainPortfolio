Production Architecture & CI/CD

Migrating Laravel 12 to AWS ECS with Dynamic Port Mapping, ALB, RDS SSL & GitHub Actions CI/CD

Deploying Laravel applications on a single EC2 instance using manual SSH commands or standalone Docker containers works fine initially, but as traffic grows, it quickly becomes brittle. You face downtime during code updates, port conflicts when restarting containers, and sluggish deployment pipelines.

⌘ GitHub Repository ↗ 📖 View Project Case Study ✦ Discuss Architecture
By Muhammad Zain Cloud & DevOps Engineer 8 min read Laravel 12 · AWS ECS · Docker · ALB · RDS MySQL SSL · GitHub Actions

Introduction

In this guide, we will walk through a production-tested architecture: migrating a modern Laravel 12 (PHP 8.2) application to AWS Elastic Container Service (ECS) with EC2 Launch Type, paired with an Application Load Balancer (ALB), secure AWS RDS MySQL, and a lightning-fast GitHub Actions CI/CD pipeline.

Why Migrate from EC2 to ECS? Standalone EC2 setups require manual container lifecycle management, suffer from port binding collisions during zero-downtime attempts, and lack automated healing. AWS ECS automates container scheduling, handles rolling deployments seamlessly behind an Application Load Balancer, and eliminates downtime completely.

Architecture Overview

Here is what our production pipeline and hosting topology looks like from code commit to user request handling:

1. GitHub Actions CI/CD

Runs automated PHPUnit test suites, compiles frontend assets with Node 22 & Vite, builds an optimized multi-stage Docker image, and pushes it to Amazon ECR with commit SHA tags.

2. Amazon ECS (EC2 Launch Type)

Orchestrates container tasks on EC2 instances using Dynamic Port Mapping (hostPort: 0), allowing old and new containers to run side-by-side during rolling updates.

3. Application Load Balancer (ALB)

Terminates SSL/TLS certificates and intelligently routes public HTTPS traffic to the dynamically assigned host ephemeral ports registered by ECS.

4. AWS RDS MySQL with SSL

Fully managed, highly available database secured via AWS RDS CA bundle certificate verification, guaranteeing encrypted transit across your AWS VPC.

Step 1: Multi-Stage Dockerfile for Laravel 12

A production Docker image must be lightweight, fast to build, and secure. We use an optimized 3-stage build to isolate build tools from runtime binaries:

  • Stage 1 (Frontend): Builds compiled assets via Node 22 and Vite, outputting only production bundles to public/build.
  • Stage 2 (Composer Builder): Installs production PHP packages without development clutter, applying optimized classmaps.
  • Stage 3 (Runtime): Lightweight Alpine Linux running PHP 8.2-FPM and Nginx, supervised together via Supervisor, with the official AWS RDS CA certificate pre-installed.
Dockerfile (Multi-Stage Production Build) 
# Stage 1: Build Frontend Assets
FROM node:22-alpine AS frontend
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm install
COPY resources ./resources
COPY public ./public
COPY vite.config.js ./
RUN npm run build

# Stage 2: Composer Dependencies
FROM composer:2 AS composer-builder
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-interaction --prefer-dist --no-scripts --no-autoloader
COPY . .
RUN composer dump-autoload --optimize --no-dev

# Stage 3: Production Runtime
FROM php:8.2-fpm-alpine AS production
RUN apk add --no-cache nginx supervisor curl bash ca-certificates \
    libpng-dev libxml2-dev oniguruma-dev libzip-dev \
    && docker-php-ext-install -j$(nproc) pdo_mysql mbstring exif pcntl bcmath xml zip

# Download AWS RDS CA Certificate
RUN mkdir -p /var/www/html/storage/certs \
    && curl -sS https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem -o /var/www/html/storage/certs/rds-ca-bundle.pem

WORKDIR /var/www/html
COPY --from=composer-builder /app /var/www/html
COPY --from=frontend /app/public/build /var/www/html/public/build
COPY docker/nginx.conf /etc/nginx/http.d/default.conf
COPY docker/supervisord.conf /etc/supervisor/conf.d/supervisord.conf
COPY docker/entrypoint.sh /usr/local/bin/entrypoint.sh

RUN chmod +x /usr/local/bin/entrypoint.sh \
    && chown -R www-data:www-data /var/www/html/storage /var/www/html/bootstrap/cache

EXPOSE 80
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["/usr/bin/supervisord", "-c", "/etc/supervisor/conf.d/supervisord.conf"]

Automated Startup Script (entrypoint.sh)

Inside docker/entrypoint.sh, automatically apply pending database migrations and cache configurations on startup, ensuring that new containers are immediately optimized and ready to serve traffic:

docker/entrypoint.sh 
#!/bin/sh
set -e

if [ -n "$APP_KEY" ]; then
    php /var/www/html/artisan migrate --force || true
    php /var/www/html/artisan config:cache || true
    php /var/www/html/artisan route:cache || true
    php /var/www/html/artisan view:cache || true
fi

exec "$@"

Step 2: The Port Conflict Problem & Dynamic Port Mapping

The Pitfall of Static Port 80

If you configure your ECS Task Definition with "hostPort": 80, you will inevitably run into this fatal deployment error:

ECS Task Failure Log 
CannotStartContainerError: Error starting userland proxy: listen tcp4 0.0.0.0:80: bind: address already in use

This happens because only one container can bind to the host's port 80. During rolling deployments, ECS tries to start the new container before stopping the old one to avoid downtime, which immediately causes a port collision crash.

The Solution: Dynamic Port Mapping (hostPort: 0)

Set "hostPort": 0 in your task-definition.json:

task-definition.json (Dynamic Port Mapping) 
"portMappings": [
  {
    "containerPort": 80,
    "hostPort": 0,
    "protocol": "tcp"
  }
]

When hostPort is set to 0:

  • Dynamic Ephemeral Port: The Docker daemon dynamically assigns a free ephemeral port from the Linux range (e.g., 32768 to 65535) to the new container.
  • Automatic ALB Registration: Amazon ECS registers the container with the Application Load Balancer Target Group on that exact ephemeral port.
  • Zero-Downtime Traffic Shift: ALB waits for the new container's health checks to pass on the dynamic port, gracefully drains the old container, and switches traffic seamlessly.
Crucial Security Group Rule: Ensure your EC2 Security Group allows inbound TCP traffic on ports 32768–65535 originating specifically from your ALB's Security Group ID. This ensures your ephemeral ports are protected from public exposure.

Step 3: Secure AWS RDS MySQL Connection

To enforce secure SSL transport encryption between Laravel and AWS RDS MySQL:

  • Store the downloaded Amazon RDS CA bundle at /var/www/html/storage/certs/rds-ca-bundle.pem (automated in Stage 3 of our Dockerfile).
  • Configure the MySQL connection options in config/database.php to verify the server certificate:
config/database.php 
'mysql' => [
    'driver' => 'mysql',
    'host' => env('DB_HOST'),
    'port' => env('DB_PORT', '3306'),
    'database' => env('DB_DATABASE'),
    'username' => env('DB_USERNAME'),
    'password' => env('DB_PASSWORD'),
    'options' => extension_loaded('pdo_mysql') ? array_filter([
        PDO::MYSQL_ATTR_SSL_CA => env('MYSQL_ATTR_SSL_CA', storage_path('certs/rds-ca-bundle.pem')),
        PDO::MYSQL_ATTR_SSL_VERIFY_SERVER_CERT => filter_var(env('MYSQL_ATTR_SSL_VERIFY_SERVER_CERT', true), FILTER_VALIDATE_BOOLEAN),
    ]) : [],
],

Step 4: High-Speed GitHub Actions CI/CD Pipeline

Many teams suffer from 15-to-20-minute pipelines. We optimized ours down to under 4 minutes using two key DevOps techniques:

  • Parallel Execution: Run automated test suites and the Docker build-and-push jobs concurrently rather than sequentially.
  • Dependency Caching: Cache Composer packages and Node modules across runs using GitHub Actions cache (type=gha).
.github/workflows/deploy.yml (Sub-4-Minute CI/CD) 
name: CI/CD Pipeline (AWS ECS)
on:
  push:
    branches: [ "main" ]

jobs:
  # JOB 1: Parallel Automated Testing
  tests:
    name: Run Automated Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.2'
          extensions: mbstring, pdo, pdo_sqlite, zip
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'
      - run: composer install --prefer-dist --no-progress
      - run: npm ci && npm run build
      - run: php artisan test

  # JOB 2: Parallel Docker Build & Push to ECR
  build-and-push:
    name: Build & Push Docker Image
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: eu-north-1
      - id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ steps.login-ecr.outputs.registry }}/laravelprojimage:${{ github.sha }}
            ${{ steps.login-ecr.outputs.registry }}/laravelprojimage:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # JOB 3: Rolling Deployment to Amazon ECS
  deploy:
    name: Deploy to Amazon ECS
    needs: [tests, build-and-push]
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: eu-north-1
      - id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2
      - name: Fetch and Render ECS Task Definition
        run: |
          aws ecs describe-task-definition --task-definition laravel-app-ec2-task --query taskDefinition > task-def.json
          jq 'del(.taskDefinitionArn, .revision, .status, .requiresAttributes, .compatibilities, .registeredAt, .registeredBy)' task-def.json > task-definition-clean.json
      - id: render-app
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: task-definition-clean.json
          container-name: laravel_app
          image: ${{ steps.login-ecr.outputs.registry }}/laravelprojimage:${{ github.sha }}
      - uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.render-app.outputs.task-definition }}
          service: laravel-ec2-service
          cluster: laravel-ec2-cluster
          wait-for-service-stability: true

Step 5: Cutting Deployment Time from 7.5 Minutes to 30 Seconds

By default, an AWS ALB Target Group takes up to 7.5 minutes to drain in-flight connections and declare new containers healthy:

  • Deregistration Delay Default: 300 seconds (5 full minutes of idle waiting during instance draining).
  • Health Check Default: 5 consecutive checks spaced 30 seconds apart (150 seconds minimum before routing traffic).

Run these two AWS CLI commands to supercharge your Target Group for rapid 30-second rolling deployments:

AWS CLI (Target Group Optimization) 
# 1. Reduce connection draining delay from 300s to 5s
aws elbv2 modify-target-group-attributes \
  --target-group-arn <TARGET_GROUP_ARN> \
  --attributes Key=deregistration_delay.timeout_seconds,Value=5

# 2. Configure fast 10-second health check verification
aws elbv2 modify-target-group \
  --target-group-arn <TARGET_GROUP_ARN> \
  --health-check-interval-seconds 5 \
  --health-check-timeout-seconds 2 \
  --healthy-threshold-count 2 \
  --unhealthy-threshold-count 2

Conclusion

By migrating Laravel 12 to Amazon ECS with Dynamic Port Mapping and an optimized Application Load Balancer, we transformed a brittle single-server setup into an enterprise-grade cloud deployment:

⚡ Zero Manual SSH

No manual SSH logins are required to pull code, restart workers, or kill old containers.

🛡️ No Port 80 Collisions

Port 80 collisions are eliminated forever using Docker ephemeral ports and dynamic ALB mapping.

⏱️ 30s ECS Rollouts

Deployments take ~30 seconds on ECS and ~3 to 4 minutes end-to-end within GitHub Actions.

🌐 100% Uptime Guaranteed

Zero-downtime rolling updates ensure users never experience broken renders or 502 Bad Gateway errors.
